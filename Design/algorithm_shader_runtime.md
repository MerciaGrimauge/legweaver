# 設計書: シェーダーと実行時の部品

対象: パッケージの `Shaders/` と `Runtime/` の働きを、自分の言葉で書いたもの（コードの写しは含みません）。
Editor 側の働きに触れる所は、ここで扱う部品との「約束」だけを書き、中身は [algorithm_editor.md](algorithm_editor.md)（以下「詳細設計 E」）に任せます。

---

## 1. 目的

### 1.1 シェーダー
タイツ・ニーハイなどの薄い編み地（以下「編み地」）を、lilToon の半透明シェーダーの派生として描く。lilToon の通常の見え方（陰影・テクスチャ・アルファなど）はそのまま使い、次の 2 点を足している。

1. **姿勢で変わる透け具合**: 関節が曲がって布が引き伸ばされる所（膝の前側など）では編み目が開いて肌が透けやすくなり、逆に縮む所（膝の裏など）では少し濃くなる。これを、スキニング後の頂点の情報だけを使って、毎フレーム頂点シェーダー・ピクセルシェーダーで近似する。CPU 側の処理やスクリプトは要らない。
2. **自分自身との重なりの破綻を防ぐ**: 半透明の三角形どうしが重なる所（下から見た両ももの間など）で、描く順番次第で暗いまだらやギザギザが出るのを避けるため、先に深度だけを書き、手前の一層だけが色を描くようにする。

この 2 点目のため、Editor 側は「姿勢で変わる透け」を使わない場合でも、透ける編み地の全マテリアルにこのシェーダーを使う（詳細設計 E 6.5）。

### 1.2 実行時の部品
アバターの体（肌）のメッシュのうち、衣装の下に残す一部の頂点について「新しいボーンの重み」を持っておくための、データだけの部品。アバターをビルドする時に Editor 側の処理がこのデータを体のメッシュの写しへ当て、部品自体は取り除かれる。実行時（ゲーム中）に動くロジックは無い。

## 2. シェーダー

### 2.1 構成（lilToon のカスタムシェーダーとしての組み立て）

lilToon の「カスタムシェーダー」の仕組みに乗っている。lilToon が用意する雛形（プロパティ一式・サブシェーダー・パス）に、こちらの部品を差し込む形で 1 本のシェーダーが生成される。構成は次のとおり。

| 部品 | 役割 |
|---|---|
| シェーダー名の定義 | 生成されるシェーダーの名前の基部を「LegWeaver」とする。インスペクターは lilToon 標準のものを使う。全パスの前に、後述の深度だけのパス（2.4）を差し込むよう指定する。 |
| 公開シェーダー（半透明版） | 名前は「LegWeaver/Transparent」。プロパティは lilToon の既定一式＋半透明用の既定一式＋本ツールの 1 項目（2.2）。lilToon の描画モード番号 2（半透明）で、カスタム計算（2.3）を取り込む。描画パス本体は隠しシェーダーから参照（UsePass）して組み立てる。 |
| 隠しシェーダー（パス置き場） | 名前は「Hidden/LegWeaver/ltspass_transparent」。同じ描画モード 2 とカスタム計算を取り込み、実際の描画パスを持つ。公開シェーダーがここのパスを参照する。 |
| カスタム計算 | 頂点で伸びの値を求めてピクセルへ渡し、ピクセルでアルファを割る（2.3）。 |
| 深度だけのパス | 色を書かずに深度だけを書く前処理パス（2.4）。 |

- 対象のレンダリングパイプラインはビルトイン（BRP）だけ。URP・HDRP 向けのサブシェーダーは定義していない。
- サブシェーダーのタグ: 種類は「TransparentCutout」、描画キューは「AlphaTest+10」（= 2460）。不透明の物（体・肌、キュー 2000 前後）より後、通常の半透明（3000）より前に描かれる。キュー 2500 以下なので、Unity の分類では不透明側として扱われ、物体単位の並べ替えは手前から奥の順になる。
- Editor 側は「描画キューが 2450 以上のマテリアル」を透けるとみなし、その部位に肌の写しを付ける（詳細設計 E 7.4）。このシェーダーのキュー 2460 はその条件に当たる。

### 2.2 入力

#### 頂点の値（メッシュ側の約束。詳細設計 E 6.6・7.2）

| 入力 | 中身 | 説明 |
|---|---|---|
| 位置 | 通常の頂点位置 | スキニング後の値が来る。 |
| 接線（tangent）の xyz | アバターの上方向（メッシュ空間。立った姿勢では脚にほぼ沿う）の単位ベクトルに、**立ち姿勢でスキニングした時に長さがちょうど 1 になるよう倍率を掛けたもの** | 長さそのものを情報として使う。シェーダーは長さだけを見て、向きは見ない。接線の入力は必ず要求される設定になっている。 |
| 接線の w | 1（固定） | 本ツールの計算では使わない。 |
| 4 番目の UV（TEXCOORD3。Unity の Mesh では UV チャンネル 3）の x | 伸びの係数 k | 「関節の曲がりの量 1 あたり、その場所の編み地がどれだけ伸びるか」。生成時に脚を曲げてみて求めた値。膝の前では正、膝の裏では負。y 以降は使わない。 |

#### マテリアルの値

| 名前 | 範囲 | 既定値 | 意味 |
|---|---|---|---|
| `_LWDynamicStretch` | 0〜2 | 1 | 姿勢による透け具合の強さ（指数）。0 以下で効果を切る。1 で計算どおり、1 より大きいと誇張、小さいと控えめ。インスペクターには表示しない（Editor 側が設定する: 姿勢の透けを使わないなら 0、不透明の引っ張り透けなら実効の強さ、それ以外は 1。詳細設計 E 6.5）。 |

そのほかのマテリアルの値（色・テクスチャ・アルファマスク・カリング `_Cull` など）は lilToon の半透明版の既定一式そのまま。

### 2.3 透け具合の計算（姿勢による伸び）

#### 原理
スキンメッシュのブレンド・スキニング（複数ボーンの変換行列を重みで混ぜる方式）では、接線のようなベクトルも混ぜた行列で変換される。曲がった関節の付近では、向きの違う回転どうしを平均するため、変換後のベクトルが短くなる。曲げが大きいほど短くなる。Unity のスキニングは接線を変換した後に長さを 1 へ戻さないので、スキニング後の接線の長さが「その頂点での関節の曲がり具合」の目安になる。

立ち姿勢で長さ 1 になるよう生成時に合わせてあるので、

- 曲がり量 c = 1 − （スキニング後の接線の長さ）
  - 立ち姿勢では c = 0、曲げるほど c は正に増える。
  - 理屈の上では長くなれば c は負になりうる（そのまま計算に使われる）。

#### 頂点シェーダー
各頂点で伸び率 s を求め、補間値としてピクセルシェーダーへ渡す（補間用のレジスタを 1 つ追加している）。

- s = 1 + k × c（k は UV の x、c は上の曲がり量）

三角形の内部では s が線形補間されるので、透け具合は面の上でなめらかに変わる。

#### ピクセルシェーダー
lilToon がテクスチャなどから色とアルファを決めた後、**アルファマスクを当てる段の直前**で、次の補正を行う。

1. 強さ d（`_LWDynamicStretch`）が 0 より大きい時だけ行う。0 以下なら何もしない（lilToon の素の見え方と同じ）。
2. 補間された s を 0.92〜3.0 に制限する: s' = clamp(s, 0.92, 3.0)。
3. 実効の伸び率 S = s'^d。
4. アルファを割る: α ← saturate(α ÷ S)（0〜1 に収める）。

考え方: 編み地が覆う割合（被覆率）は、伸びた分だけ薄くなる（面積あたりの糸の量が 1/s になる）とみなし、アルファを s で割る。

下限 0.92 の理由: 実際の編み地は縮む所では詰まるより皺になるので、濃くなる量を小さく抑える。これより下げると、元々濃いかかとが、つま先を伸ばした姿勢でほぼ不透明になる。上限 3.0 は極端な値の保険。

まとめた式:

α_out = saturate( α_in ÷ clamp(1 + k·(1 − |T_skinned|), 0.92, 3.0)^d )　（d > 0 の時）

アルファマスクはこの後に lilToon の通常の処理で当たる（Editor 側は、立った姿勢での伸びの分布を「乗算」のアルファマスクとして与える。詳細設計 E 6.5）。

### 2.4 描画の順序と工夫（深度の前処理パス）

公開シェーダーの全パスの前に、次の性質のパスを 1 つ足している。

- 色は一切書かない（カラーの書き込みマスク 0）。
- 深度を書く（ZWrite 有効）。深度比較は既定（手前か同じなら通す）。
- カリングはマテリアルの `_Cull` に従う（本体の描画と同じ面を対象にする）。
- ライトモードは「Always」（ライトの有無にかかわらず毎回描く）。
- 頂点はオブジェクト空間の位置を普通にクリップ空間へ変換するだけ。アルファ・テクスチャは見ない（切り抜きもしない）。

手順としては、1 つの物体について

1. まずこのパスで、衣装の全三角形の深度を書く。結果として、各ピクセルには衣装の「いちばん手前の面」の深度が残る。
2. 続いて lilToon の半透明の本体パスが色を描く。深度比較で、いちばん手前の面と同じ深度のピクセルだけが通り、奥にある衣装自身の面は描かれない。

効果: 衣装が自分自身と重なる所でも、半透明が二重三重に重なって描く順番によって濃さが変わる、という破綻が起きず、手前の一層だけが半透明で見える。衣装の下の肌（または肌の写し。写しは深度を少し奥へずらして描く）は、キューの順番（2.1）で先に描かれているので、手前の一層を通して透けて見える。

### 2.5 本体パス
本体の色の描画（前面・背面・影など）は lilToon の半透明版の標準パスそのまま（隠しシェーダーから参照）。本ツールが変えたのは、2.3 のアルファ補正と、そのための頂点からの値の受け渡しだけ。

## 3. 実行時の部品（体の頂点の重みの付け替えデータ）

### 3.1 位置付け
- アバターの中に置く、データだけを持つ部品（名前は「SkinFollow」）。追加メニューには表示しない（ツールが自動で置く）。
- VRChat の「エディター専用」の印が付いており、アップロード時のビルドではアバターから取り除かれる。実行時に処理は無い。
- 実行時用のアセンブリに入っているのは、ビルドの段階までシーン・プレハブにデータとして保存しておくため。アセンブリは VRChat SDK 以外を参照しない。

### 3.2 持つデータ
対象の体の SkinnedMeshRenderer 1 つへの参照と、次の 4 本の配列。可変長の「頂点ごとの重みの一覧」を、圧縮した行形式（行ごとの件数＋平らに並べた本体）で表している。

| 配列 | 長さ | 中身 |
|---|---|---|
| 頂点番号 | N | 新しい重みを与える体のメッシュの頂点番号。 |
| 件数 | N | 各頂点が、下のボーン・重みの列のうち何件を使うか。 |
| ボーン番号 | M（= 件数の合計） | 体のレンダラーのボーン配列の中の番号。 |
| 重み | M | ボーン番号と同じ並びの重み。 |

読み方: i 番目の頂点（0 始まり）のボーン・重みは、件数の 0〜i−1 番目の合計を開始位置として、そこから件数[i] 件分を順に取る。

### 3.3 いつ・何をするか
1. 生成時（Editor 側。詳細設計 E 8.5）: 透ける衣装で下に着る物（下着など）を見せる時、その下に残す肌の頂点について、下に着る物と一緒に動くよう新しいボーンの重み（その点での下着のウェイトの上位 4 本、正規化）を求め、衣装のオブジェクトに付けたこの部品に入れる。頂点番号は昇順。
2. アバターのビルド時（Editor 側。NDMF の変換の段、Avatar Optimizer の最適化より前）: 体のメッシュの写しを作ってこの重みを当て、レンダラーのメッシュを写しに差し替える（元のメッシュアセットは変えない）。その後この部品は取り除かれる。エディター上では NDMF のプレビュー（レンダーフィルター）が同じ差し替えを代理のレンダラーで見せる。
3. 実行時: 何もしない（部品は残っていない）。

目的: 衣装が姿勢で動いた時、下の肌が衣装と違う動きをして衣装から突き抜けるのを防ぐ。

### 3.4 データの妥当性の約束
- 件数の合計 = ボーン番号の長さ = 重みの長さ。
- 1 頂点あたりの件数は 1〜255。
- 頂点番号は体のメッシュの頂点数未満、ボーン番号は体のバインドポーズの数未満。
- 各頂点の重みの合計は 1（生成側が正規化して書く。当てる側では検査しない）。
- 部品自身は中身を確かめる処理を持たない。ビルド時に当てる Editor 側の処理が上の約束を確かめ、合わなければ警告を出してメッシュをそのまま残す（別のアバターのプレハブから部品が来た場合の備え）。

## 4. 制約・既知の限界

### シェーダー
- **接線の長さに情報を載せている**ため、次の場合に効果が壊れる、または消える。
  - メッシュの読み込み・最適化・別ツールの処理で接線が再計算・正規化された場合（立ち姿勢で長さ 1 という前提が崩れる。全部 1 になれば c は常に 0 になり効果が消える）。
  - スキニングで接線を正規化する環境・設定の場合。
  - メッシュがスキンメッシュでない、またはボーン 1 本だけに付いている頂点は、曲げても長さが変わらないので効果が出ない。
- c は「重みの異なるボーンどうしの回転の差」から生じる量なので、ボーンの重みがはっきり 1 本に分かれている所では関節でも小さい。伸びの大きさは生成時の k で補う前提。ねじり（向きを変えない回転）や伸縮スケールでも長さは変わるので、意図しない変化が出うる。
- 接線の**向き**はメッシュから再計算した物ではなくアバターの上方向に置き換わるので、利用者がこのマテリアルにノーマルマップを足すと、凹凸の向きが UV の向きとずれる（本ツールが作るマテリアルはノーマルマップを使わない）。
- 伸び率 s は頂点で求めて線形補間するので、三角形が大きい所では透け具合の変化が粗くなる。
- 下限 0.92 により、縮む側の濃くなり方は最大でも約 1/0.92 ≈ 1.087 倍（d = 1 の時）。
- 姿勢の係数 k は 1 つの姿勢（股関節 70・膝 100・足首 30 度）で較正してあるので、別の姿勢（開脚・ひねりなど）では誤差が出る。腕の衣類には使わない（詳細設計 E 6.6）。
- 深度だけのパスはアルファを見ないので、**アルファ 0 の所（テクスチャの穴、透明に抜いた所）も深度を書く**。その結果、
  - 同じ衣装の、穴の奥にある面は描かれない。
  - キューが後の物（2460 より後に描く通常の半透明の物など）が衣装の奥にあると、衣装の透けた部分越しに見えなくなる。
- 深度だけのパスは lilToon の頂点処理（輪郭線の押し出しなど頂点を動かす機能）を通らないので、そういう機能を使うと本体と深度がずれうる。
- BRP 専用。Android（Quest）ではカスタムシェーダーが使えないため対象外。

### 実行時の部品
- 部品はデータを持つだけで、中身を確かめる処理を持たない（確かめるのはビルド時の Editor 側）。
- 体のメッシュの頂点やボーンの並びが生成後に変わると、ビルド時の確かめで弾かれるか、範囲内のまま別の頂点に当たる（範囲内の食い違いは見分けられない）。
- ビルド時に当てる処理（Editor 側。NDMF が必要）が無いと何の効果も無い。
